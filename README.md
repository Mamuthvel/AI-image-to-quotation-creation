# Limras Quotation Desk

Reads a customer's handwritten materials list and turns it into a priced quotation.
Staff correct anything the system flagged, then print.

---

## Run it

```bash
npm install
cp .env.example .env      # optional - see "Vision" below
npm start                 # http://localhost:3000
npm test                  # 15 regression tests
```

With no API key set, uploading any image loads the bundled sample sheet. The whole
demo works offline this way — useful for showing the client before spending on keys.

## Vision

Set one key in `.env`:

```
VISION_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
```

or

```
VISION_PROVIDER=gemini
GEMINI_API_KEY=...
```

The vision model does one job: transcribe the page. It is told **not** to guess brands
or sizes, and to transcribe misspellings as written. All item resolution happens in
deterministic code afterwards, so accuracy does not drift when the model changes.

## How a line gets matched

```
"Switan domy — 50"
   ↓  normalize.js    ditto marks, ½ → .5, phonetic repair
"switch dome"
   ↓  attributes.js   category + structured spec
{ category: SWITCH_DOME, colour: null }
   ↓  matcher.js      filter on stated attrs, rank the rest
SWITCH DOME WHITE @ ₹4.50  ·  state: assumed  ·  "colour not specified — using WHITE"
```

Matching is attribute-based, never string similarity. `"20 Amps switch"` shares almost
no characters with `E-CLASS WH 20A 1WAY SWITCH`, but `{amps: 20, category: SWITCH}`
matches it exactly.

Candidates are ranked by: attributes the customer stated → shop default brand for that
category → sales frequency. A stated attribute the SKU cannot satisfy disqualifies it
outright, so the system returns *no match* rather than a confidently wrong one.

### The four row states

| Rail | State | Meaning |
|---|---|---|
| green | **Confirmed** | The description named everything needed |
| blue | **Assumed** | Brand or size came from shop defaults — reason shown on the row |
| amber | **Check this** | Another item scores almost as well, or confidence fell under 50% |
| red | **No match** | Nothing in the master fits — pick it manually |

Rails follow the Indian wiring colour code, so staff read row status the same way they
read a conductor. Amber and red are what the counter has to look at; green and blue can
be trusted at a glance.

## Tuning accuracy

Three files, no code changes needed:

**`server/data/defaults.json`** — the single biggest lever. `brandByCategory` decides
what gets quoted when the customer just writes "6 amps switch". `attrDefaults` breaks
ties (a plain switch beats the indicator version). `thresholds` controls when a row goes
amber.

**`server/data/aliases.json`** — phonetic spellings and category synonyms. Seeded from
the sample sheet: `switan → switch`, `plugo → plug`, `sai older → batten holder`.

**`server/data/items.json`** — the item master, 227 SKUs, alphabetical. Generated by
`npm run seed`. **Replace this with Limras's real export before any pilot.** Every row
needs `category`, `brand`, `uom`, `rate`, and parsed `attrs` — the flat name string alone
will not match. Normalising their real master into this shape is the main remaining work.

### It learns

Every manual override calls `POST /api/learn`, writing the customer's exact phrasing to
`server/data/learned-aliases.json`. That phrasing resolves instantly next time, at 100%.
Month three is materially faster than month one.

## API

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/health` | SKU count, vision status |
| GET | `/api/items?q=` | Item search for the picker |
| POST | `/api/extract` | `{image, mediaType}` base64 → matched lines |
| POST | `/api/parse-text` | `{text}` typed list → matched lines |
| POST | `/api/rematch` | `{text, qty}` → one re-matched line |
| POST | `/api/learn` | `{text, sku}` → record a correction |
| GET/POST | `/api/quotations` | List / save |

## What it does beyond matching

- **Quantity expressions.** `2+1+2+5+2` is kept verbatim next to the total, because that
  is how the staff verify against the sheet.
- **Sum conflicts.** If the sheet's written total disagrees with its own addition, the row
  is flagged. Line 2 of the sample sheet does exactly this.
- **Ditto marks.** A lone `"` inherits the previous line's item. A `"` immediately after a
  digit is an inch mark. Both cases are tested.
- **Agreed price.** Captures the negotiated figure alongside the calculated total —
  the ₹14,500-on-a-₹15,902-quote situation.
- **Print output** mirrors the shop's existing quotation layout.

## Not built yet

Deliberately out of scope for the demo:

- GST breakup and HSN codes
- Customer master, quote → order → invoice flow
- Per-customer brand preferences (the ranking hook exists; the data does not)
- Auth and multi-user
- A real database — quotations and learned aliases are JSON files

## Stack note

Plain HTML/CSS/JS frontend on Express, no build step, two dependencies. The matching
engine (`server/services/`) has no framework ties, so porting the UI to React later is a
UI-only job.

---

## Before a pilot

1. Get the real item master exported and normalised into the `attrs` shape.
2. Sit with the counter staff and fill in `brandByCategory` from what they actually quote.
3. Collect 50–100 matched pairs — customer sheet plus the quotation that came from it —
   and measure how many lines resolve with zero edits. That number, not a demo, is what
   tells you whether this replaces their software.
